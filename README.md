# Simple Mock Server

Универсальный HTTP mock/proxy-сервис для тестирования. 
Работа сервера осуществляется через сессии. Каждая сессия знает адрес основного сервера, куда пересылает все запросы, кроме тех запросов, которые подменяются. Содержит состояния сценария и изолированный журнал. 

Управление доступно через Web-панель, HTTP API и MCP. 

## Требования

- .NET SDK 10 (версия зафиксирована в global.json).
- Node.js 24 и npm (версия Node указана в web/.nvmrc).
- Доступ к NuGet/npm при первой установке.

Backend: ASP.NET Core, EF Core и SQLite. 
Frontend: Angular 21.

## Запуск

Из корня проекта:

```bash
dotnet restore
cd web
npm ci
cd ..
./scripts/dev.sh
```

Панель: [localhost:4200](http://localhost:4200). Backend: [localhost:5080](http://localhost:5080). Ctrl+C останавливает оба процесса.

Раздельный запуск:

```bash
dotnet run --project src/MockServer.Api --no-launch-profile
```

В другом терминале:

```bash
cd web
npm start
```

## Собранная версия

```bash
./scripts/build.sh
cd dist/server
dotnet MockServer.Api.dll
```

Панель и API работают в одном процессе на [localhost:5080](http://localhost:5080). Для публикации нужен SDK, для запуска достаточно .NET 10 Runtime с ASP.NET Core. Запускайте из dist/server для предсказуемых путей к БД, настройкам и статическим файлам.

## Docker

Нужны Docker Engine и Docker Compose. Из корня проекта:

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f mock-server
```

Панель: [localhost:5080/sessions](http://localhost:5080/sessions), API и MCP работают
на том же порту. Образ собирает Angular на Node 24 и backend на .NET SDK 10;
в рабочем контейнере остаются ASP.NET Core Runtime и собранная панель. Процесс
работает от непривилегированного пользователя. Проверка `/health` отображается
в состоянии контейнера.

Используются [официальные образы ASP.NET Core 10](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/docker/building-net-docker-images?view=aspnetcore-10.0).

SQLite хранится в `/data/mock.db` внутри постоянного volume `mock-data`.
Сессии и журнал сохраняются при перезапуске, пересборке и `docker compose down`.
Команда `docker compose down --volumes` удаляет этот volume вместе с базой.
Локальные базы и каталог `work` не попадают в образ.

Остановка и последующий запуск:

```bash
docker compose down
docker compose up -d
```

### Существующая база

По умолчанию контейнер создаёт новую базу в volume. Для базы с `cabinet-staging`
используйте каталог `work` как bind mount и укажите имя файла. Сначала остановите
другой экземпляр сервера, работающий с этой базой. Важно подключать каталог целиком,
чтобы SQLite сохранял рядом файлы WAL/SHM.

```bash
MOCK_DATA_SOURCE=./work \
MOCK_DATABASE_FILE=published-sessions-smoke.db \
MOCK_UID="$(id -u)" MOCK_GID="$(id -g)" \
docker compose up --build -d
```

Для повторных запусков с этой базой используйте те же переменные. Их можно сохранить
в локальном `.env` в корне проекта; файл исключён из Git и контекста сборки:

```dotenv
MOCK_DATA_SOURCE=./work
MOCK_DATABASE_FILE=published-sessions-smoke.db
# UID и GID владельца файлов, значения из id -u и id -g
MOCK_UID=501
MOCK_GID=20
```

В примере UID/GID показаны для macOS; подставьте значения своей системы.
Миграции применяются автоматически, существующие сессии и журнал сохраняются.
Перед первым обновлением базы можно сделать согласованную копию через SQLite backup.

### Порт, LAN и upstream на компьютере

По умолчанию порт доступен только на самом компьютере. Для другого порта:

```bash
MOCK_PORT=5090 docker compose up -d
```

Для телефона в локальной сети:

```bash
MOCK_BIND_ADDRESS=0.0.0.0 docker compose up -d
```

Адрес подключения телефона: `http://LAN-АДРЕС:5080/s/{id}`. Если браузер приложения
использует другой origin, задайте его через `MOCK_ALLOWED_ORIGIN`. Для дополнительных
origin добавьте `AllowedOrigins__1`, `AllowedOrigins__2` в environment сервиса.

Если upstream запущен на компьютере, в конфигурации сессии замените его `localhost`
на `host.docker.internal`, например `http://host.docker.internal:3000`.
Compose добавляет этот адрес и для Docker Engine на Linux. Для upstream в другом
контейнере используйте имя его сервиса и общую Docker-сеть. На Linux сервер
upstream должен принимать подключения со стороны Docker-сети.

[Результаты проверки Docker](docs/verification-docker.md).

## Работа с сессией

1. Откройте панель и создайте HTTP-сессию.
2. Укажите название, `upstreamBaseUrl` и правила `rules`.
3. Сохраните и возьмите адрес подключения приложения: `/s/{id}`.
4. Используйте этот адрес как base URL; путь API добавляется после него.
5. Проверьте журнал, переключите состояние или сбросьте сессию для повторного прогона.

Маршруты и ответы определяет пользователь. Можно сопоставлять method/path/query/headers/form/JSON, задавать статус, задержку, заголовки и тело. Путь может быть точным или содержать отдельные сегменты `{name}`. `protectedPaths` запрещает fallback для выбранных путей; неоднозначные совпадения дают диагностическую ошибку.

[Формат правил, HTTP API и подключение мобильных устройств](docs/http-sessions.md).

## MCP для агента

Endpoint: `/mcp`, транспорт Streamable HTTP. Для Codex:

```bash
codex mcp add simple-mock --url http://localhost:5080/mcp
```

15 инструментов позволяют создавать и редактировать сессии/правила, переключать состояния, смотреть подробности и удалять записи журнала, проверять запросы, импортировать/экспортировать конфигурации. Агент и панель используют одну прикладную логику.

## Хранение и сеть

По умолчанию SQLite хранится в `data/mock.db` относительно content root процесса. Для постоянного расположения задайте абсолютный `DatabasePath`. Миграции применяются при запуске. Сессии, состояние и журнал переживают перезапуск. Журнал находится на отдельной вкладке сессии: поиск, фильтры, подробности запроса и ответа, удаление выбранных записей либо всего журнала без сброса состояния. Записи доступны страницами без ограничения общего количества; автоматического удаления старых записей нет.

Сохраняются query, заголовки и тела обеих сторон (до 256 KiB каждое), время, размеры, адреса, протокол, traceId и переход состояния. Известные секретные поля маскируются в заголовках, query, JSON, XML и формах. Multipart сохраняет поля и метаданные файлов. Усечённые или некорректные структурированные тела могут быть пропущены с объяснением. Сжатые тела gzip/br/deflate распаковываются с ограничением размера перед маскированием, неподдерживаемое кодирование пропускается. Бинарные тела сохраняются в base64; произвольные секреты в бинарных данных, тексте и путях автоматически распознать нельзя. Подробности появляются только у новых записей.

Один процесс сервера на одну БД. Для резервной копии используйте SQLite backup либо копирование остановленной БД с учётом WAL/SHM.

По умолчанию сервер слушает loopback. Для телефона нужен доступный LAN-адрес компьютера, сетевой listener и разрешённый origin приложения. Панель и MCP предназначены для доверенного локального окружения; пользовательская авторизация отсутствует. Остальные запросы действительно исполняются на выбранном backend.

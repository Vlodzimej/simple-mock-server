# HTTP-сессии Simple Mock Server

Сессия определяет произвольные маршруты HTTP без изменения кода сервера. Никакие пути приложения и имена action в движке сессий не зафиксированы.

## Быстрый старт

1. Запустите сервер по README и откройте `/sessions`.
2. Нажмите «Новая HTTP-сессия», задайте name, upstreamBaseUrl и rules в JSON. Сохраните.
3. Возьмите «Адрес подключения приложения» и используйте его как base URL. Добавляйте существующие пути API после `/s/{id}`.
4. Выполните проверку в приложении. «Обновить запросы» показывает выбранные правила, статус и причины отказов.
5. «Сбросить состояние и журнал» возвращает initialState без удаления правил. Экспорт и импорт переносят сценарий между запусками/компьютерами; импорт всегда создаёт новую сессию.

Пример конфигурации (демонстрационные маршрут и ответ):

```json
{
  "name": "Проверка ошибки обновления",
  "upstreamBaseUrl": "https://test.example.com",
  "proxyEnabled": true,
  "initialState": "started",
  "protectedPaths": ["/v2/items/{itemId}"],
  "rules": [
    {
      "id": "update-error",
      "priority": 10,
      "match": {
        "method": "PATCH",
        "path": "/v2/items/{itemId}",
        "json": { "accountId": 42 }
      },
      "response": {
        "status": 422,
        "delayMs": 500,
        "json": { "success": false, "message": "Тестовая ошибка" }
      }
    }
  ]
}
```

Замените upstreamBaseUrl на реальный адрес тестового backend. При пустом адресе или `proxyEnabled: false` запросы без моков возвращают 502. Настройки каждой HTTP-сессии независимы. Поля `id` и `state` управляются сервером; редактирование state в конфигурации не переключает сценарий, для этого есть отдельные API/MCP-операции.

## Сопоставление запросов

- `path` обязателен, начинается с `/`, чувствителен к регистру и завершающему `/`. Точный путь либо отдельные непустые сегменты `{name}`, например `/orders/{id}`. Имя сегмента обозначает шаблон и не подставляется в ответ.
- `method` по умолчанию `*` (любой метод), сравнение без учёта регистра.
- `query`, `headers`, `form`: объекты строк. Все указанные условия должны совпасть; дополнительные поля запроса разрешены. Query/form ожидают одно значение; имена заголовков сравниваются без учёта регистра.
- `form` поддерживает URL-encoded и multipart; файловые части не сопоставляются. При fallback исходное тело, включая multipart, передаётся backend.
- `json` сопоставляет рекурсивное подмножество объекта. Массивы и примитивы сравниваются целиком. Явный `json: null` означает JSON null; отсутствие поля означает отсутствие условия. Для JSON-условия нужен JSON Content-Type.
- Все условия правила объединяются через AND. Правила с `enabled: false` выключены.
- Меньший `priority` выигрывает; по умолчанию 100. Несколько совпадений одного лучшего приоритета дают 409 с id конфликтующих правил. Запрос на backend не отправляется.
- `whenState` ограничивает правило состоянием сессии; `nextState` резервирует новое состояние при выборе правила, до задержки и отправки ответа. Запросы внутри сессии выполняются последовательно, поэтому переход применится один раз. Отмена клиентом после выбора правила не откатывает переход. Рекомендуемый способ «первый вызов ошибка, следующий успех»: два правила для одного пути с разными whenState, первое переводит во второе состояние.

Если совпадения нет, сервис отправляет запрос в upstream. Например, `upstreamBaseUrl: https://backend.example/base` и запрос `/s/{id}/orders?x=1` дают `https://backend.example/base/orders?x=1`. Метод, исходный escaping пути, повторяющиеся query, заголовки авторизации и тело сохраняются. Hop-by-hop заголовки исключаются. Redirect возвращается клиенту без автоматического перехода. Domain cookies и абсолютные Location не переписываются.

`protectedPaths` закрепляет пути за моками: без подходящего правила возвращается 409. Используйте для изменяющих данные операций, которые должны оставаться локальными даже при ошибке настройки сценария. Ошибка совпавшего мока и некорректное анализируемое тело не включают fallback.

## Ответ

`response`: status (200 по умолчанию), delayMs (0), headers (объект), json либо text. JSON может быть объектом, массивом, примитивом или null; без json/text тело пустое. По умолчанию Content-Type: application/json для JSON и text/plain для text; заголовком можно задать свой тип, в том числе text/html. HEAD не возвращает тело. 204/205/304 с телом отклоняются. Служебные Content-Length, Transfer-Encoding, Connection и подобные заголовки задаются сервером.

Ограничения: 100 правил и 100 защищённых путей, конфигурация до 512 KiB, задержка до 30000 мс, входящее тело до 1 MiB, текст/JSON ответа до 262144 символов, условие JSON до 65536 символов. Неизвестные поля конфигурации отклоняются, чтобы опечатка в условии не расширяла область мока. Регулярных выражений, скриптов и интерполяции ответов нет.

## HTTP API

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/admin/api/sessions` | Список полных конфигураций |
| POST | `/admin/api/sessions` | Создание конфигурации, 201 с id |
| GET/PUT/DELETE | `/admin/api/sessions/{id}` | Чтение, полная замена, удаление |
| PUT/DELETE | `/admin/api/sessions/{id}/rules/{ruleId}` | Изменение одного правила |
| PUT | `/admin/api/sessions/{id}/state` | `{"state":"retried"}` |
| POST | `/admin/api/sessions/{id}/reset` | initialState и очистка журнала |
| GET | `/admin/api/sessions/{id}/export` | Конфигурация без id/state/истории |
| POST | `/admin/api/sessions/import` | Конфигурация как новая сессия |
| GET | `/admin/api/sessions/{id}/requests?limit=100&ruleId=...` | Последние запросы; limit до 5000 |
| POST | `/admin/api/sessions/{id}/verify` | Проверка количества вызовов |

Тело verify: `{"ruleId":"update-error","method":"PATCH","path":"/v2/items/42","count":1}`. Фильтры необязательны; путь точный, count по умолчанию 1. Ответ: `{"matched":true,"actualCount":1,"expectedCount":1}`. Проверка относится к сохранённым последним 5000 запросам сессии. Панель показывает последние 100. Журнал не хранит query, тела и заголовки; URL path сохраняется. Не помещайте секреты непосредственно в путь.

Создание через файл экспорта:

```bash
curl -sS http://localhost:5080/admin/api/sessions/import \
  -H 'Content-Type: application/json' --data-binary @session.json
```

HTTP 400: конфигурация/тело невалидны; 404: сессия/правило отсутствует; 409: конфликт правил либо защищённый путь; 502: fallback невозможен или ошибка upstream; 504: timeout upstream. Прокси ограничен 30 секундами на запрос. Петля между сервером и посредником останавливается по маркеру экземпляра до ожидания блокировки сессии.

## Управление агентом через MCP

HTTP transport доступен на `/mcp`, использует официальный MCP C# SDK. Для локального Codex:

```bash
codex mcp add simple-mock --url http://localhost:5080/mcp
```

Эта команда добавляет подключение в конфигурацию Codex; автоматически проект её не выполняет. После подключения обновите список MCP-инструментов в клиенте. Для другого MCP-клиента задайте тот же URL как Streamable HTTP endpoint.

Инструменты: create_session, list_sessions, get_session, update_session, delete_session, upsert_rule, delete_rule, set_scenario_state, list_requests, verify_requests, reset_session, export_session, import_session. `list_sessions` и `list_requests` возвращают объект `{"items":[...]}`. Создание возвращает id и basePath `/s/{id}`. Полный адрес устройства складывается из доступного адреса сервера и basePath. Все операции используют ту же прикладную логику, что и панель/API.

Пример задачи агенту:

> Создай отдельную сессию для этой задачи с моим тестовым backend. Подмени PATCH /items/{id}: первый вызов верни 503, повторный 200. Запрети fallback для этого пути. Дай адрес подключения телефона. После прогона проверь, что каждое правило сработало один раз, и экспортируй конфигурацию.

Состояние MCP-транспорта и тестовые сессии независимы: переподключение агента не удаляет сценарии. SQLite хранит сессии, состояния и журнал после перезапуска. Запускайте один экземпляр сервера на одну БД: последовательность запросов обеспечивается внутри процесса.

## Физические устройства

Backend по умолчанию слушает loopback. Для LAN используйте запуск из README с `--urls http://0.0.0.0:5080`, явно разрешёнными origin приложения и доступным портом. Base URL телефона: `http://LAN-АДРЕС:5080/s/{id}`; для стандартного Android Emulator: `http://10.0.2.2:5080/s/{id}`. В Angular dev-режиме `/s/…` и `/mcp` тоже проксируются, поэтому адрес панели можно использовать как адрес сервера, если dev-сервер доступен телефону.

Изменения base URL внутри debug-сборки, QR/deep links, разрешение HTTP/доверие сертификатам и публичный HTTPS-деплой не выполняются этим проектом. Панель и MCP предназначены для доверенной локальной сети и пока не имеют пользовательской авторизации. Реальные вызовы, не покрытые моками, действительно выполняются на выбранном backend. Вебхуки провайдеров, push и сетевые вызовы нативных SDK вне этого base URL не перехватываются.
